<objective>
Close the D-05 carry-forward from the Phase 40 code review: add the outbound HA bearer
token (`HA_ACCESS_TOKEN`, read from `.env`) to the log-redaction secret set so that when
Phase 42's `announceOrStartConversation()` sends `Authorization: Bearer ${HA_ACCESS_TOKEN}`,
the token value can never appear in any `log.*` output.

Purpose: Phase 42 is the first place the outbound HA token is sent in a request header.
The redaction infrastructure (`registerSecrets`/`redact` in `src/logger.ts`) already exists
and is wired at `src/index.ts:95` via `registerSecrets(extractSecretValues(config))`, but
`extractSecretValues()`'s `case 'home-assistant': break` pushes nothing — the token is never
registered. This plan patches that one branch and pins it with a test.

Output: A patched `extractSecretValues()` and a config test asserting the HA token is
extracted for redaction when a home-assistant channel is present.
</objective>

From src/config.ts (the branch to patch — extractSecretValues, ~lines 396-416):
- `extractSecretValues(config: Config): string[]` walks `config.heads[].channels` and
  pushes per-vendor credential strings into a local `candidates: (string | undefined)[]`,
  then appends each candidate with `typeof v === 'string' && v.length >= 8` into `out`.
- The home-assistant branch is currently: `case 'home-assistant': break  // token is global (HA_ACCESS_TOKEN), not per-channel`
- `HA_ACCESS_TOKEN` is already in `ENV_KEY_ALLOWLIST` (src/config.ts ~line 510). It is NOT a
  per-channel config field — it lives in `process.env`.

From src/logger.ts:
- `registerSecrets(values: string[])` stores values with `v.length >= 8`; `redact()` then
  `replaceAll`s each registered value with `[REDACTED]` in every `log.*` argument.

From src/index.ts (~line 95):
- `registerSecrets(extractSecretValues(config))` is called once at startup. Anything
  extractSecretValues returns is redacted in all subsequent logs.
