## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator browser (React) → /api/sensors | the page issues authenticated fetches; all filesystem authority lives server-side (Plan 01). The frontend never touches the filesystem directly. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-49-02-CLIENTSLUG | Tampering | client-side slug derivation in new-sensor form | mitigate | Client slug derivation is UX convenience only; the server (Plan 01 `SLUG_RE` guard) re-validates every slug on PUT/DELETE and is the authority. A malformed client slug cannot bypass the server guard. |
| T-49-02-AUTHZ | Information Disclosure | /api/sensors fetches | accept (inherited) | All `/api/sensors` routes are gated by the existing `requireAuth` middleware server-side (Plan 01 T-49-01-AUTHZ); the dashboard fetch wrapper carries the session. No new auth surface added here. |
| T-49-02-RUNFEEDBACK | (UX, not security) | run-on-save | accept | `runSensor` always resolves and routes errors to the ambient file (Phase 48 design / Pitfall 3). The UI documents this ("check sensor output for errors") rather than wrapping the runner — by design, not a vulnerability. |
| T-49-02-SC | Tampering | npm installs | accept | No new packages (RESEARCH.md "no installs"); legitimacy gate N/A. |
</threat_model>
