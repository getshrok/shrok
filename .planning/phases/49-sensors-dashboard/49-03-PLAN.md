## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator browser → POST /api/schedules | the form posts `headId` + `taskName` (sensor slug) + `kind:'script'`; the server validates headId against the live head list and persists the row. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-49-03-HEADID | Spoofing / Tampering | AddSensorScheduleForm headId seed | mitigate | headId is seeded from `'active-head'` localStorage and validated server-side against the live head list (existing `POST /api/schedules` 404-on-unknown-head, unchanged). A forged/absent headId is rejected by the server, not silently accepted. |
| T-49-03-AUTHZ | Information Disclosure | /api/schedules + /api/sensors fetches | accept (inherited) | Both routes are gated by the existing `requireAuth` middleware (Plan 01 for sensors; pre-existing for schedules). No new auth surface. |
| T-49-03-KINDBYPASS | Tampering | kind:'script' skips tasksLoader check | accept (by design) | Plan 01 intentionally leaves the `tasksLoader.load(taskName)` existence check inside the `kind==='task'` branch, so a script slug is not validated against the tasks loader. The sensor slug is operator-supplied and only used as a filename by the runner (slug-guarded at run time per Phase 48). No traversal: the runner re-validates the slug. |
| T-49-03-SC | Tampering | npm installs | accept | No new packages (RESEARCH.md "no installs"); legitimacy gate N/A. |
</threat_model>
