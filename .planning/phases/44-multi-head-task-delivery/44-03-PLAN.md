<objective>
Add `deliverToHeadIds` input validation and persistence to the schedules API: accept it task-only on POST, validate every id against the live head set (404 on unknown), dedupe, treat empty as absent; and on PATCH allow editing/clearing the delivery set while keeping the owner-`headId` reassignment ban intact.

Purpose: This is the untrusted-input boundary of the phase. The HTTP body is the only place attacker-controlled data enters; it must be validated (array shape, non-empty strings, every id a known head, deduped, task-only) before it reaches the store and ultimately the completion fan-out. Mirrors the Phase 35 D-11 admin-404 stance and the D-13 no-headId-reassignment ban exactly.

Output: edits to `src/dashboard/routes/schedules.ts` (POST + PATCH) and `src/dashboard/routes/schedules.test.ts`. Depends only on Plan 01 (the store/types). Independent of Plan 02 — runs in its own wave but could overlap; kept at Wave 3 for a clean tsc boundary after the spawn-path wave.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-06 | Tampering / Information disclosure | unvalidated `deliverToHeadIds` injecting an arbitrary/unknown head into the delivery set (would route a task completion to an unintended head) | mitigate | Validate at route entry: `Array.isArray` + every element a non-empty string + every id present in `resolveCurrentHeads()` (404 on unknown, no silent fallback — D-11). Only known heads can ever enter the persisted set. |
| T-44-07 | Tampering | scope creep — `deliverToHeadIds` accepted on a reminder (out of scope, D-01) | mitigate | Task-only guard: reminders with the field return 400 on both POST and PATCH (the stricter/clearer behavior). |
| T-44-08 | Elevation of privilege | bypassing the D-13 owner-reassignment ban via the new field | mitigate | The new field is a distinct key; the existing `bodyObj['headId'] !== undefined` guard is untouched. A test pins that PATCH with `headId` still returns 400. The delivery set is editable; ownership is not. |
| T-44-09 | Denial of service | oversized/duplicate-heavy `deliverToHeadIds` array | accept | Deduped via `Set` before persistence; effective size is bounded by the configured head count (single-digit). No explicit length cap needed beyond the known-head validation, which inherently bounds distinct valid ids. The route is behind `requireAuth` (admin-only surface). |
| T-44-SC | Tampering | npm/pip/cargo installs | accept | No new packages (code-only edits + tests). No legitimacy gate required. |
