## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dashboard form → POST/PATCH /api/schedules | The form sends `deliverToHeadIds`, but the authoritative validation lives server-side (Plan 03). The client control merely restricts choices to known heads for UX; it is not a security control. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-10 | Tampering | client could send arbitrary `deliverToHeadIds` bypassing the UI multi-select | mitigate (server-side) | The server route (Plan 03) re-validates every id against `resolveCurrentHeads()` (404 on unknown) and enforces task-only. The dashboard control is convenience only; trust is on the server. No client-side validation is relied upon for security. |
| T-44-11 | Information disclosure | XSS via head id rendered in a chip | accept | Head ids are React-rendered as text content (auto-escaped) and are themselves validated server-side to be known config head ids — not free-form user text. No `dangerouslySetInnerHTML`. |
| T-44-SC | Tampering | npm/pip/cargo installs | accept | No new packages (UI edits to existing files only). No legitimacy gate required. |
</threat_model>
