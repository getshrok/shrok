<objective>
Wire the delivery set through the live spawn → run → complete path: pass it at the scheduled spawn site (activation.ts), preserve it across resume, and — the core change — fan out `agent_completed` to every delivery head at BOTH top-level completion sites, while gating scheduled agents out of question-suspension.

Purpose: This is where "deliver to many heads" actually happens. The expensive work (the agent) runs exactly once; each delivery head's activation loop independently claims its own `agent_completed` event and runs its own relay/work-summary stewards. The two fan-out sites are the primary pitfall: `completeAgent` is the end-of-turn path, and the `ctx.complete` closure in `buildAgentExecutor` is the tool-driven early-exit path — missing either silently delivers to the owner only. The question gate (D-06) removes the only execution-time head-routing ambiguity (a scheduled run has no human to answer).

Output: edits to `src/sub-agents/local.ts` (fan-out ×2, question gate, resume preservation) and `src/head/activation.ts` (spawn pass-through). Depends on Plan 01's types/persistence.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| schedule store → spawn → agent record | The delivery set read from the schedule (already validated by Plan 03's route on write) flows into SpawnOptions and is persisted on the agents row. No external untrusted input crosses here — the schedule was validated at API write time. |
| agent completion → queue (per-head routing) | The fan-out stamps `head_id` on each enqueued `agent_completed`. The routing target set is `dedupe([this.headId, ...deliverToHeadIds])` — bounded by the heads validated at schedule-write time. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-44-03 | Information disclosure | fan-out delivers a completion to an unintended head | mitigate | The delivery set is validated against `resolveCurrentHeads()` at API write time (Plan 03); it is then persisted on the agent and read back verbatim. A head removed between write and completion simply has no activation loop to claim its event (harmless dead enqueue). No silent broadening occurs — the set never grows past what was validated. |
| T-44-04 | Denial of service | unbounded fan-out enqueues | accept | The delivery set is length-bounded by the number of configured heads (single-digit in practice) and validated at the route layer (Plan 03 enforces each id is a known head; duplicates are deduped). Each head independently runs its own stewards — intended cost, the expensive agent work runs once. |
| T-44-05 | Repudiation/elevation | scheduled agent suppressing a legitimate question | accept | By design (D-06): a scheduled run has no human attached to answer. The question text is preserved as the completed output and still delivered to all heads, so nothing is lost — it is surfaced as a completion rather than stranded as a suspended-question with no answerer. |
| T-44-SC | Tampering | npm/pip/cargo installs | accept | No new packages (code-only edits to existing files). No legitimacy gate required. |
