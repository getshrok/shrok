<objective>
Create the `/v1/chat/completions` HTTP router — the inbound leg's request/response surface. The router validates the inbound bearer token (JSON 401, no `WWW-Authenticate`), extracts the last user turn (400 if absent), generates/echoes `conversation_id`, sets up the `pendingReply` promise + deadline timer against the adapter, registers `req.on('close')` cleanup, dispatches the inbound message non-blockingly, and serializes the head's reply via `buildChatCompletionResponse` when it lands inside the deadline — or lets the turn lapse with no body when it does not (D-01). Verification is a standalone Express test (no live HA, no device), driving `adapter.send()` directly to simulate the head's reply.

Purpose: This is the central inbound contract — HACV-01..05, SC4, and D-04 all land here. It composes Plan 01's types and Plan 02's adapter slot lifecycle into a working held-connection endpoint testable without a real HA device.
Output: `router.ts` (factory + deadline constant) and `router.test.ts` (the Wave-0 integration suite).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HA (cross-origin) → /v1/chat/completions | Untrusted bearer-presenting client crosses into Shrok; the router is the authn + input-validation gate |
| held HTTP connection → head reply | The router drives the pendingReply slot; deadline/close paths must not leak |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-41-07 | Spoofing | unauthorized turn injection (no/invalid bearer) | mitigate | Inline bearer check at the top of the handler; JSON 401 with NO `WWW-Authenticate` on missing/invalid token (HACV-02); pinned by the 401 tests |
| T-41-08 | Spoofing | Apache Basic-401 confusion | mitigate | Shrok's 401 carries no `WWW-Authenticate` header so HA/tests distinguish it from Apache's Basic 401; acceptance asserts the header is absent |
| T-41-09 | Information Disclosure | bearer key in logs | mitigate | Router never logs the `Authorization` header or `inboundApiKey`; only `log.info` on generated conversation_id and `log.error` on unexpected rejection messages |
| T-41-10 | Denial of Service | many held connections / leaked timers | mitigate | `req.on('close')` clears timer + slot (SC4); D-04 single-slot replacement bounds live state to one Promise per adapter; deadline timer rejects + clears |
| T-41-11 | Tampering | `messages[].content` injection | accept | Content flows to the head's normal text pipeline (same as all adapters); LAN-only + bearer-gated; no extra sanitization |
| T-41-12 | Tampering | `conversation_id` spoofing → thread `ha-${id}` | accept | Internal thread key; an attacker with a valid bearer + known id could inject into that thread — acceptable under the LAN-only + bearer threat model |
</threat_model>
