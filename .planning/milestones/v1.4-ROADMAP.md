# Milestone v1.4: Unmissable Reminders

**Status:** ✅ SHIPPED 2026-05-24
**Phases:** 37-39
**Total Plans:** 9

## Overview

An opt-in reminder severity that nags on a configurable interval until the user explicitly
acknowledges it — so high-stakes reminders (appointments, meds) can't fire into the void.
The nag re-arms in code at the scheduler/activation layer *before* delivering the current
fire, so nagging never depends on the head doing work each cycle. Ack semantics differ by
type (one-time → delete; recurring → stop this occurrence's nag loop while the base cron
continues). Dashboard reminder forms expose the `requiresAck` + nag controls and a
start-date/time picker for recurring schedules/reminders/tasks (folded-in backlog 999.1).

**Success Criteria:**
1. An ack-required reminder fires, arms the next nag before delivery, and keeps re-firing on the nag interval without any head action between cycles
2. Acknowledging a one-time ack-required reminder removes it entirely — no further nags
3. Acknowledging a recurring ack-required reminder stops the current nag loop while the base cron continues future occurrences
4. When ack is received, the already-armed in-flight nag is cancelled rather than allowed to fire
5. The injected fire event includes the reminder ID and ack instructions; the ack tool is scoped so it never applies to an ordinary reminder

## Milestone Summary

**Key Decisions:**

- `create_reminder` description pre-advertises nag-until-acknowledged behavior before the runtime exists (D-10b) — foundation phase ships schema + params; description becomes fully true when Phase 38 lands. Ratified over REVIEW CR-01's soften recommendation (Phase 37)
- Nag fields creation-only at first (D-09, Phase 37) — **superseded by D-11 in Phase 39**: ack/nag fields are editable post-create via `SchedulePatch`/`update()`; toggling ack off while nagging cleans up the in-flight nag (D-11/D-12)
- System-native nag re-arm placed first in `tick()`'s advance block so it never hits the one-time disable path (Phase 38)
- WR-01 hardening: channel-outage delete guarded with `!requiresAck` so ack reminders survive outages and re-nag (Phase 38)
