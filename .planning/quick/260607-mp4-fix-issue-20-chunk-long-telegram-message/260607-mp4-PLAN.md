Purpose: long agent replies (tables, code dumps, multi-section answers) reach the user instead of vanishing.
Output: `src/channels/telegram/split.ts` (pure helper), `split.test.ts`, chunked `send()`/`sendDebug()` in `adapter.ts`, CHANGELOG entry.

  <action>
Create `src/channels/telegram/split.ts` exporting a single pure function:

`export function splitMessageForTelegram(text: string, render: (s: string) => string, limit = 4096): string[]`

`render` is supplied by the caller so the helper measures the REAL output (table width expansion + HTML), per D-locked approach. The function returns an array of SOURCE chunks (not rendered) — the caller renders each chunk itself before sending.

Algorithm:
1. Split `text` on '\n' into lines. Walk lines and group into ATOMIC blocks that must never be split internally:
   - (a) Fenced code block: a line whose trimmed value starts with ``` opens a block; collect through the next line whose trimmed value starts with ``` (inclusive). If no closing fence is found before EOF, treat the rest of the input as the block (unterminated fence).
   - (b) Table run: a maximal contiguous run of lines where each is a table row (use the isTableRow regex above). A run is its own atomic block.
   - (c) Every other line is its own one-line block, splittable freely on '\n' (i.e. each non-atomic line is an independent unit you may place in any chunk; you may also pack multiple such lines into one chunk).
2. Greedy accumulation: maintain a `current` list of source lines for the in-progress chunk. For each block, form `candidate = (current.length ? current.join('\n') + '\n' : '') + block.join('\n')`. If `current` is empty, the block is the candidate. If `render(candidate).length <= limit`, append the block's lines to `current`. Otherwise: flush `current` (join with '\n', push to output) and start a fresh chunk with this block — UNLESS the block ALONE over-renders, in which case go to step 3.
3. Over-cap single block fallback (block's own `render(block.join('\n')).length > limit`):
   - First flush any pending `current`.
   - Table/plain blocks: hard-split on LINE boundaries — greedily accumulate the block's own lines into sub-chunks, measuring render() of each sub-candidate, flushing when the next line would exceed the cap. A single line that still over-renders falls back to CHARACTER-boundary slicing so no piece ever exceeds the cap (slice the source line into pieces small enough that render(piece) <= limit; a conservative loop that shrinks the slice until it fits is acceptable).
   - Fenced code blocks: strip the opening/closing ``` lines, hard-split the inner content on line (then char) boundaries as above, and RE-WRAP each piece with the SAME opening fence line (preserve any language tag) + a closing ``` line so every emitted piece is a valid standalone fenced block. Account for the fence overhead when measuring against the cap.
   - Push each resulting piece as its own chunk.
4. After the loop, flush any remaining `current`.
5. CRITICAL regression guarantee: if the whole input renders within the limit, return `[text]` (the single original string) so the caller's render(chunk) is byte-identical to today's `render(text)`. Implement this as an early check: if `render(text).length <= limit` return `[text]` immediately.

Keep split.ts dependency-free (inline the isTableRow/isSeparatorRow regexes; do NOT import from table-formatter — the helper must stay pure and render-agnostic). Respect noUncheckedIndexedAccess (guard every `lines[i]` / `arr[0]`) and exactOptionalPropertyTypes.
