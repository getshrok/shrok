<objective>
Fix the incomplete skill/task rename so a rename cascades across EVERY reference, not just same-kind skill-deps. Today `FileSystemKindLoader.renameSkill` only moves the directory and rewrites same-kind `skill-deps`. It misses (1) the renamed entry's OWN frontmatter `name:`, (2) schedule `taskName` (orphans scheduled tasks — the live bug we hand-fixed), (3) cross-kind `skill-deps` (a TASK pointing at a renamed SKILL), and (4) `usage.target_name`. It also gives no warning when the old name lingers in freeform body text.

Because `renameSkill` is kind-scoped it cannot see the other loader, ScheduleStore, or UsageStore. The cascade orchestration lives on `UnifiedLoader.rename`, which spans both loaders and receives the two DB stores as deps. The kind route prefers `unifiedLoader.rename` when wired and falls back to the bare `renameSkill` otherwise (back-compat).

Purpose: A rename should leave zero dangling references; scheduled tasks must keep firing; usage attribution must follow the rename. Lookup is by DIRECTORY name — frontmatter `name` is display metadata that must be kept in sync.
Output: Enhanced loader, new UnifiedLoader.rename cascade, ScheduleStore.renameTask, UsageStore.renameTarget, richer rename route + wiring, dashboard warning surfacing, and full test coverage. Final gate: `npx tsc --noEmit` + `npx vitest run` green.
</objective>
